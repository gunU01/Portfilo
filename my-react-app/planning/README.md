# 기획 하네스와 구축 계획

사이트의 검증 하네스(`harness/`)가 코드의 구조와 동작을 기계로 검사하듯, 이 하네스는 **기획 문서의 연결과 근거의 정직함**을 기계로 검사합니다. 첫 대상은 `projects/sosang`(오늘한입, 동네 사장님 5분 홍보)입니다.

## 왜 만들었나

기획 문서는 쓰는 동안은 그럴듯해도, 시간이 지나면 어긋납니다. 요구사항은 있는데 구현 기능이 없고, 기능은 있는데 어떤 문제 때문인지 알 수 없고, '검증됐다'고 쓴 문제에 근거가 2차 자료뿐입니다. 이 하네스는 그런 어긋남을 사람이 읽다가 발견하기 전에 기계가 먼저 잡습니다.

## 다섯 가지 원칙

1. **모델이 단일 원천이다.** 기획 내용은 `projects/<이름>/model/` 의 데이터로만 적고, 읽는 문서(`docs/`)는 거기서 만들어 낸다. 문서를 직접 고치면 `plan:build --check` 가 잡는다.
2. **확인 상태를 정직하게 적는다.** 모든 근거는 `원문 확인 / 2차 자료 / 검색 요약만 봄 / 확인 자료 없음` 중 하나다. 2차 자료만으로는 문제를 `validated` 로 바꿀 수 없다(EVD-03).
3. **사람이 해야 하는 일은 사람에게 돌려준다.** 인터뷰와 실험 결과는 기계가 만들 수 없다. 하네스는 문서가 통과해도 '현장 확인 대기'로 따로 표시하고, 다음에 할 일을 목록으로 만든다.
4. **범위에 한도를 둔다.** MVP 기능은 5개를 넘지 못하고(SCP-01), '하지 않는 것'을 5개 이상 적어야 한다(SCP-02).
5. **하네스도 검사한다.** `selftest.mjs` 가 일부러 망가뜨린 모델로 모든 규칙이 실제로 반응하는지 확인한다.

## 구조

```
planning/
  harness/
    schema.mjs     항목 종류와 필수 필드
    rules.mjs      규칙 23개
    gates.mjs      규칙 → 6단계 판정, 현장 확인 대기 항목 계산
    check.mjs      검사 실행(CLI)
    render.mjs     모델 → 문서
    build.mjs      문서 생성 / --check 로 최신 여부 확인
    tally.mjs      인터뷰 집계(합격선 충족 여부 계산)
    selftest.mjs   하네스 자체 시험
  projects/sosang/
    model/         기획 내용(데이터). 여기만 고친다
    docs/          자동 생성 문서 13개
    reports/       현황 보고서(자동 생성)
    field/         현장 조사: interview-guide.md(질문지·요청 메시지), templates/(기록 양식), data/(실제 기록, 저장소에 올라가지 않음)
```

## 쓰는 법

```
npm run plan         자체 시험 + 검사 + 문서가 최신인지 확인
npm run plan:check   검사만(단계 판정과 현장 확인이 남은 일을 보여 줌)
npm run plan:build   model/ 에서 docs/, reports/ 를 다시 만듦
npm run plan:test    하네스 자체 시험
npm run plan:tally   인터뷰 기록(field/data/*.csv) 집계
```

### 인터뷰 결과를 넣는 방법

결과는 사람이 직접 확인한 근거이므로 표본 수(`n`)와 날짜가 반드시 필요합니다(EVD-02).

```js
// model/evidence.mjs
{ id: 'E-11', kind: 'interview', claim: '인터뷰 10명 중 7명이 지난 한 달 홍보를 0~1회 했다', n: 10, date: '2026-11-05',
  status: 'verified', ref: { type: 'none', value: '인터뷰 기록(개인 노트)' }, checkedAt: '2026-11-05' },
```

그다음 `experiments.mjs` 의 T-01 을 `status: 'done'` 으로 바꾸고 `result` 를 적고, 합격선을 넘었다면 `hypotheses.mjs` 의 H-01 을 `supported`, `problems.mjs` 의 P-01 을 `validated` 로 바꿉니다. 근거가 모자라면 하네스가 오류로 막습니다.

## 단계(게이트)

| 단계 | 무엇을 보는가 | 통과 뜻 |
| --- | --- | --- |
| G1 프레임 | 항목 형식, ID, 연결 | 문서의 뼈대가 맞다 |
| G2 근거 | 출처, 확인일, 표본 수 | 근거가 정직하게 적혀 있다 |
| G3 해결안 | 문제 → 요구사항 → 기능 → 화면 → 지표 | 끊김이 없다 |
| G4 사업성 | 수익 입력값의 기준, 지표 목표의 근거 | 가정이 가정으로 표시된다 |
| G5 검증 설계 | 모든 가설에 실험과 합격선 | 무엇으로 맞고 틀림을 가릴지 정해졌다 |
| G6 범위 | MVP 한도, 하지 않는 것, 과장 표현 | 범위가 통제된다 |

각 단계는 `통과 / 문서 통과 · 현장 확인 대기 / 실패` 로 나옵니다. '현장 확인 대기'는 문서는 맞지만 인터뷰·실험으로 확인할 것이 남았다는 뜻이며, 지금은 대부분 이 상태입니다.

## 구축 계획

기간은 제안값입니다. 인터뷰 경로에 따라 달라지며, 문채원 님이 조정합니다.

### 0단계 — 하네스와 첫 모델 (완료)

- 노션의 후보 주제와 하위 조사 문서 5개를 읽고 모델로 옮겼다(문제 5, 가설 7, 실험 5, 요구사항 11, 기능 10, 화면 5, 지표 8, 위험 8, 의사결정 8).
- 이후 소상공인실태조사 보고서와 경쟁사 공식 페이지 4곳을 직접 읽어 `원문 확인` 근거를 8건으로 늘렸다. 인터뷰·설문·실험으로 직접 확인한 근거는 아직 0건이다.

### 1단계 — 정리와 확인 (1주, 2026-10-20 시작)

2026-10-20 문채원 님이 "일단 지금 이대로 시작하자"고 하여 의사결정 D-01~D-08과 합격선 5개를 확정했다(`decidedBy`, `decidedAt`에 기록). 확정은 근거가 바뀌면 다시 본다.

| 할 일 | 누가 | 상태 | 끝났다는 기준 |
| --- | --- | --- | --- |
| 의사결정 D-01~D-08 확정 | 문채원 | 완료 | 모두 accepted |
| 제안 합격선 5개 확정 | 문채원 | 완료 | `thresholdBasis: 'owner'` |
| 인터뷰 질문지·기록 양식·집계 도구 | Claude | 완료 | `field/interview-guide.md`, `templates/`, `plan:tally` |
| 인터뷰 경로 확보(T-05, A-01) | 문채원 | 해야 함 | 경로 2개 이상, 요청할 사장님 명단 |
| 시장·경쟁사 자료 확인(T-04) | 문채원(접속 가능한 환경) | 일부 완료 | 소상공인 실태조사는 확인(E-06, 07, 16, 17). E-08, 09, 10, 15는 남음 |

### 2단계 — 문제 확인 (2주)

- 요식업 사장님 10명 인터뷰(T-01). 요청 수와 수락 수를 함께 기록한다.
- 끝나면 근거 장부에 결과를 넣고 `npm run plan` 으로 검사한다.
- **판단 시점**: 아래 표로 다음 단계를 정한다.

| 결과 | 다음 |
| --- | --- |
| H-01, H-07 합격선 충족 | 3단계로 간다 |
| H-07 만 미달(수락률 낮음) | 접근 경로를 바꿔 요청 수를 늘린다(T-05) |
| H-01 미달 | 문제 정의를 다시 쓴다. P-02(이탈 단골)나 다른 세그먼트(D-01)로 옮길지 검토한다 |
| 둘 다 미달 | 이 주제를 접고 노션의 다른 후보로 간다. 접는 과정 자체를 기록한다 |

### 3단계 — 해결안 확인 (3~4주)

- 컨시어지 2주(T-02): 가게 5곳에 사람이 직접 '오늘 할 일 1개'와 문구를 보낸다.
- 랜딩 사전 신청(T-03)을 같은 기간에 병행한다.
- 수행률 50% 미만이면 대행형 쪽 전환을 검토한다(D-02, K-02).

### 4단계 — 정리와 반영 (1주)

- 결과를 근거 장부에 넣고 문제 상태를 `validated` 또는 `rejected` 로 바꾼다.
- 포트폴리오에 싣는다. 확인되기 전에는 '문제, 가설, 설계, 검증 계획'으로만 쓰고 결과를 사실처럼 쓰지 않는다(D-08).
  - 사이트: `src/data/` 에 케이스 하나를 추가하고, 근거가 있는 수치만 쓴다.
  - 피그마: 비어 있는 A4-7, A4-8 자리에 넣는다.

### 포트폴리오 반영 (2026-10-20, 1차)

인터뷰 없이 정량 근거만으로 피그마 포트폴리오에 4쪽(A4-7 프로젝트 개요, A4-8 시장 데이터, A4-9 해결 방향과 검증 설계, A4-10 수익성과 경쟁 서비스)을 넣었다. 개요 쪽은 얼마·해미와 같은 형식이며 포인트 색은 연두(해미는 주황)다. 기존 대회·학력은 A4-11이 되었다. A4-7의 '소감'은 초안이며 직접 고쳐야 한다.
- 쓴 것: 소상공인실태조사 원문 수치(E-06, E-07, E-16, E-17), 이 수치에서 계산한 규모, 가설 합격선, 해지율 가정에 따른 계산, 공식 페이지로 확인한 경쟁사 요금(E-11~E-14).
- 쓰지 않은 것: 출처 확인 전인 업종 구성비(E-15), 기사와 표가 맞지 않는 배달앱 광고비(E-09), 확인하지 못한 경쟁사 요금(E-10, 한계 표에는 '미확인'으로 표기).
- 모든 문제는 가설이며 인터뷰·컨시어지·랜딩은 하지 않았다고 본문에 적었다(D-08).
- 피그마에서 모델을 다시 만드는 자동화는 없다. 모델의 수치가 바뀌면 A4-7~10도 직접 고쳐야 한다.

## 아직 확인하지 못한 것

- 배달앱 월 평균 광고비(E-09): 기사는 107만 780원, 보고서 표 캡처는 107,780원으로 10배 차이가 난다. 보고서 원문이 필요하다.
- 경쟁사 요금(E-10): 도도포인트, 스마트단골은 확인하지 못했다. 노션의 값을 그대로 옮겼다.
- 업종 구성비(E-15)와 음식점업 사업체 수(E-08): 표 제목·출처 확인이 필요하다.
- 소상공인 실태조사에는 SNS 홍보 활용과 홍보를 못 하는 이유를 묻는 문항이 없다. 그 부분(H-01, H-02)은 인터뷰로만 확인할 수 있다.
- 인터뷰, 컨시어지, 랜딩 결과는 아직 없다.
